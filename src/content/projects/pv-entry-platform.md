## 背景与约束

户用光伏的业务链条很长：获客、进件、勘探、安装、并网、巡检、售后、仓配。每一个环节背后都有一套或几套存量系统，代理商和内部员工要在不同系统之间切换，重复登录、反复查找。

2026.08，我接手这个平台的产品规划。目标是 2026.10 底上线 MVP，11 月持续迭代；留给产品、研发和联调的时间只有 3 个月。

约束也很明确：

- 存量系统不能停，也不能大改；业务在跑，没有窗口做整体重构。
- 三端都要覆盖：App、小程序、PC 门户；但团队和时间不允许三端各做一套。
- 用户包括内部员工、代理商和个人用户，角色不同，能看到和能操作的范围也不同。

## 问题定义

这不是「再做一个 App」的问题，而是：**在不重构存量系统的前提下，把分散的入口收成一个可用的统一入口。**

如果重写，3 个月不可能；如果只做一个导航页，用户还是要反复登录、找不到待办、不知道下一步去哪。真正要解决的是四件事：

1. **统一入口**：用户从一个地方进来。
2. **统一账号**：不用每个系统记一套账号。
3. **统一权限**：不同角色看到不同的内容。
4. **统一运营**：内容能持续更新，而不是每次改版都找研发。

## 我的角色与边界

我是产品经理，负责范围定义、方案设计、取舍、排期和上线验收。

我不负责存量系统内部的改造，也不替代各业务系统的办理能力；我的边界是「入口、账号、权限、运营配置」，办理仍然发生在原系统。

协作方包括业务方、研发、上下游系统团队和运营。这个项目最难的不是画页面，而是让多个系统团队接受同一套接入方式，并在 3 个月内完成联调。

## 方案

### 三端分工：同一功能只在一端建设

- **小程序负责获客**：轻量、易传播，承接线索和注册。
- **App 负责现场作业**：勘探、安装、巡检等需要移动能力。
- **PC 门户负责统一入口和管理看板**：信息密度高，适合管理和配置。

三端不是「功能对齐」，而是「按场景分工」。同一个功能只在一端建设，避免三端重复开发和后续维护。

### 统一入口 + 免登：不重构，换 3 个月

存量系统继续运行，不做重构。平台通过统一账号和免登接入，把入口收拢到一个地方；用户登录一次，就能进入有权限的系统。

这个方案放弃了一部分改造自由度：各系统的 UI、交互和数据模型不会完全统一。但它换来了 3 个月上线，以及业务不停机。对当时的业务窗口来说，这是更重要的目标。

### 运营配置：把内容更新交给运营

平台的内容不是写死的。运营可以自助发布内容，系统设敏感词审核；编排细化到栏目和区块级；可见性按身份定向，不同角色看到不同的首页。

这样做的好处是运营响应快，不需要每次改文案都排研发；代价是产品团队要设计好配置边界和审核规则，避免内容失控。

## 关键取舍

| 选择 | 放弃 | 理由 |
|---|---|---|
| 不重构存量系统 | 彻底的架构统一、深度改造 | 3 个月窗口；业务不能停；重构收益慢于上线 |
| 统一入口 + 免登 | 各系统 UI / 交互完全一致 | 先解决「找得到、进得去」，再谈体验统一 |
| 同一功能只在一端建设 | 三端功能完全对齐 | 避免重复建设，保证 3 个月交付 |
| 运营自助配置 | 产品团队集中管控所有内容 | 运营响应更快；用敏感词审核和身份定向控制风险 |

## 结果

- 2026.10 底 MVP 上线，11 月持续迭代。
- 户用业务各环节已在新平台承接。
- 一批存量系统不重构，通过统一入口和免登接入。
- 从规划到 MVP 上线，3 个月。

## 复盘

如果重来，我会更早统一账号和权限模型。入口整合看起来是导航问题，实际是权限和身份问题；这两件事越早定，后面的联调和运营配置越省返工。

「不做重构」不是偷懒，是算过时间、风险和业务连续性的取舍。但上线后要补一份技术债清单，明确哪些系统、哪些接口、哪些体验需要在下一阶段收敛。
